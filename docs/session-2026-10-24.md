# AgentWall: session record (2026-10-24)

*Generated 2026-10-24. Branch `docs/methodology-refresh` on `grugrog/agentwall`, commit `6cf42da`
(on top of `9bd2890` and the initial commit `06d7def`). No pull request has been opened.*

AgentWall is a detect-and-report system that works at the web/HTTP layer. It catches rogue AI-agent
behaviour modelled on the two 2026 incidents: Medicare (blocked, found workarounds, read non-public
files, wrote to the server) and Hugging Face (indirect prompt injection, with C2 and exfiltration on
ordinary public services). It uses only the Python 3 standard library. Positioning: a feature plus
a service, sold through MSPs and anchored to the ACSC High alert of 25 Sep 2026. It does no
enforcement and never hacks back (Criminal Code Part 10.7).

### 1.2 METHODOLOGY.md refresh (commit `9bd2890`)
These parts of METHODOLOGY.md no longer matched the code:
- The §5.2 table had old numbers (98.2%, block-defiance 97.5%, low-and-slow 96.0%, 4.4s). Updated.
- The eval sorts each attack into block-defiance or low-and-slow by the median gap between
  requests. That is a scoring rule, not a detector property, so sessions can move between those two
  rows from run to run. Compare overall recall, not the per-type split.
- §4 said "three detectors". There are four; §4.4 was added for `kill_chain`.
- §6: the **9 remaining misses** were inspected one by one. All are **failed grinds**: a deny, then
  5–10 evasion variants, every one answered 401/403/404, with no breakthrough. By the detector's
  definition, not alerting on them is correct.
- New §11 covers cross-tenant correlation. It was previously undocumented.
- Bug fixed: `CrossTenantCorrelator.ingest()` used `return a or b`. When one signal completed both
  tiers, the second alert was marked fired and then lost. `ingest()` now returns a list, and
  `ingest_many()` delegates to it. Gated by unit check #7.

### 1.3 Full project review (commit `6cf42da`)
Each fault below was reproduced first. Each new gate **fails on the old code and passes on the fix**.

| # | Fault | Impact | Fix | Gate |

| 2 | Web Bot Auth suppression was keyed on the **/24** | One verified agent in a cloud or NAT /24 hid any attacker in that range | Keyed per session; the unverified-agent severity upgrade is per session too | unit #9 |

## 3. Decisions for Grug
1. **Should verified agents be suppressed at all?** A Web Bot Auth–verified agent that defies a
   block is currently suppressed. The Medicare agent was a legitimate vendor's agent, so a verified
   signature might well have suppressed the headline incident. Option: downgrade it to a
   lower-severity "verified agent defied a block: notify the operator" alert instead of dropping it.
   The behaviour is unchanged for now; this needs your call.
2. **Alert on failed grinds?** The 9 misses are failed grinds. A local, lower-severity "attempted
   defiance" alert would catch them, but it needs its own false-positive gate on the benign and NAT
   suites first. Today the correlator covers them across tenants.
3. **The LLM-artifact regex** (`thought:`, `action:`, `as an ai`) is likely to cause false positives
   on real form bodies (contact forms, blog comments). It is only medium severity, and it only runs
   where bodies are sampled. Tune it once real traffic exists.

## 4. Known design limits (unchanged)
- Actor identity is the source /24. In production, upgrade to ASN or a JA4H/header-order hash.
- `kill_chain` egress stages join the *customer server's* /24, not the inbound attacker's, so the
  egress leg only correlates when both share a range.
- Bodies are rarely in access logs, and egress needs its own feed.
- Simulation is not production.
